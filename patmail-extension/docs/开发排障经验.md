# 开发排障经验

记录已通过代码、抓包或浏览器复现确认的结论。每条区分已修复的问题、可复用的排查方法和仍未解决的边界。

## 2026-10-27：并发打满同源连接会把「检测慢」报成「掉登录」

完整现场证据见 [命名批量与掉登录误判修复](download-name-batch-and-session-2026-10-27.md)。

### 现象与根因

下载命名 6 路并发打满同源 6 条连接时，`GetUserModel` 会话检测排不上队，15 秒被掐成 `REQUEST_TIMEOUT`（DevTools 里的 canceled 就是插件自己 abort 的）。而检测失败被写成 `error`/`expired` 并清空身份，工作台随即显示「尚未连接 / 请先登录」——「检测慢」被报成「掉登录」，还会滚出更多检测请求。

### 经验一：只有服务端明确说没登录才算掉登录

`IsLogin=false`、登录页跳转、HTTP 401 是权威结论；超时、网络、网关、畸形响应只是「这次没读到」。已登录状态只能被权威结论推翻，检测失败保持现状并如实报错，业务请求真掉登录会自己报 `SESSION_EXPIRED`。

### 经验二：canceled 不一定是用户取消

DevTools 里的 canceled 先看发起方和时长：插件为超时主动 abort 的请求也会显示 canceled。15–16 秒的 canceled 就是 15 秒时限的痕迹，别当成「用户点了取消」。

### 经验三：并发打满浏览器同源连接数会饿死小请求

同一主机 6 条连接全被长请求占满时，心跳、会话检测这类小请求会排队到超时。长任务（命名、打包）留出连接余量，比事后重试更省。

## 2026-10-27：同一批文件下载两次，一个 fetch 一个 xhr

完整现场证据见 [下载去点证据、双下载根因与下载进度](file-download-stream-progress-2026-10-27.md)。

### 现象与根因

`222.har` 里同一批 1605 个文件有两条 `Call=DownLoad`：一条 fetch（插件 `content.js`），一条 xhr（原站 `FileSearch.js → public.js`），浏览器下载两次。带点的文件名来自原站那条：原站自己的「下载」按钮（`#btn_Down → FileManager.DownFile → GetFileName → Success → DownLoad → GetFile`）被页面跑了一遍，它不做申请号去点。插件链路 1605 个名字逐条检查去点残留为 0。

### 经验一：HAR 判发起方先看 resource type，再看 initiator 栈

DevTools 的类型列 fetch/xhr 直接区分插件与原站代码；`_initiator.stack` 的顶层帧是 `content.js` 就是插件，落在 `jquery.js → public.js → 页面js` 就是原站。不要凭“插件只发一次”推断另一条是谁的。

### 经验二：缺失的请求先怀疑录制窗口，不要急着怀疑代码

原站那条链路的 `GetFileName` 不在 HAR 里：1605 个名字的单次命名跑了十几分钟，请求早于录制开始，完成时间正好接上它的 `Success → DownLoad`。判缺失请求是否“没发过”，先和录制起点、服务端耗时对齐。

### 边界

插件不拦截、也不模拟原站下载按钮；两个包会互相排队占用服务器打包时间。使用口径写在 [README](../README.md)：同一批文件只点插件「下载已选」。

## 2026-10-27：打包成功，但浏览器没有保存文件

完整现场证据见 [下载停住排查报告](download-troubleshooting-2026-10-27.md)。

### 现象与根因

用户点击下载后停住；原站 `DownLoad` 返回 HTTP 200 和 `file_guid`，但浏览器没有下载记录。

本次已复现的根因是内容脚本运行在 EASY 的 HTTP 页面上，发送后台消息时直接调用了 `crypto.randomUUID()`。该 API 在这个非安全上下文中不存在，代码抛出 `TypeError`，因此 `SAVE_DOWNLOAD` 消息尚未发出，后续 iframe 兜底也没有执行。

### 经验一：按下载阶段定位，不能把 XHR 完成当作落盘成功

| 阶段 | 需要检查的证据 | 能说明什么 |
| --- | --- | --- |
| 生成文件名 | `GetFileName` 响应、名称数量与文件数量 | 下载参数准备完成 |
| 服务端打包 | `DownLoad` 响应、`file_guid`、失败文件数 | 服务器提供了取包句柄 |
| 通知后台 | 内容脚本异常、消息 ID、`SAVE_DOWNLOAD` 请求与响应 | 下载任务是否交给后台 |
| 浏览器取包 | `FileHandler.ashx` GET、浏览器下载 ID | 浏览器是否开始接收文件 |
| 保存完成 | 下载状态 `complete`、接收字节数、磁盘文件 | 文件是否确实保存 |

XHR/fetch 接收完响应、拿到文件 GUID、浏览器接受下载任务、文件落盘，是不同的完成条件。界面的“成功”必须说明对应哪个阶段。

页面 HAR 可能不包含扩展后台发起的下载请求。HAR 里缺少 `FileHandler.ashx` 时，还要检查后台及浏览器下载记录，不能只凭缺失请求下结论。

### 经验二：内容脚本要按宿主页面的实际环境验证 API

扩展后台和工作台可用的浏览器 API，不一定在 HTTP 页面的内容脚本里可用。检查实际执行上下文中的 `isSecureContext` 和 API 是否存在。

本次消息关联 ID 最初在后台通信工具中增加兼容分支，后续已抽到 [newUuid 公共实现](../src/utils/uuid.ts)，[后台通信工具](../src/utils/runtime.ts) 调用该函数：

```ts
const requestId = newUuid()
```

`getRandomValues()` 可在非安全上下文使用。公共函数将16个随机字节排成36字符的带连字符 ID；消息协议只要求 ID 非空且不超过80字符。本文链接公共实现，不再复制旧的32字符内联版本，避免经验文档与当前代码漂移。

参考：[randomUUID 的安全上下文要求](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID)、[getRandomValues 的上下文说明](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues)。

### 经验三：原站的通用错误字段必须结合具体接口协议解释

本次 `DownLoad` 同时返回 `error=true`、有效 `file_guid` 和“共0个文件下载失败”。按已确认的原站协议，这种响应仍可继续取包，不能只看到 `error=true` 就中止。

判断规则限定在该下载接口：确认登录状态，读取有效取包句柄，再识别失败文件数；有失败文件时保留提示。不能推广成“所有接口只要有 GUID 就成功”。协议依据见 [文件操作接口文档](../../API/06-文件操作.md)。

### 经验四：通用错误提示会掩盖跨组件交接处的异常

页面最终只显示“页面读取失败”时，应回溯其 catch 分支。通过 DevTools 对已捕获异常暂停，找到实际抛错语句和调用栈，再追踪请求是否跨过下一组件边界。

本次异常发生在发送消息之前，延长接口超时、反复打包或增加后台重试均不能解决。先确定失败阶段，再改对应代码。

### 经验五：回归测试必须保留触发问题的环境

jsdom、HTTPS 和 localhost 测试环境可能提供 `randomUUID()`，掩盖真实 HTTP 页面的缺陷。

- 单元测试显式移除 `randomUUID`，保留真实 `getRandomValues`，验证消息能够发送、响应能够返回、监听能够清理。
- 并发测试让响应乱序返回，验证不同消息 ID 不会串线。
- 浏览器测试使用非 localhost 的 HTTP 地址，断言 `isSecureContext=false`、`randomUUID` 不存在。
- 通过本地代理返回夹具；代理不转发业务请求，并拒绝 CONNECT，避免测试访问真实服务器。
- 除接口响应外，还校验浏览器下载记录为 `complete`，磁盘字节与 ZIP 夹具一致。

回归入口：[消息通信测试](../tests/unit/ui/runtime-messaging.test.ts)、[浏览器下载测试](../tests/e2e/download.e2e.mjs)。构建后在扩展项目目录运行 `npm run test:e2e:download`。

本次记录：修复前回归用例因相同 TypeError 失败；修复后相关 18 项测试通过，全量 124 个测试文件、805 项测试通过，类型检查及两段构建通过，隔离浏览器完成取包及磁盘字节校验。这些是本次验证结果，不代表后续版本自动通过。

### 经验六：重新加载扩展后，还要更新已注入页面的脚本

更新构建产物后，重新加载扩展，再刷新 EASY 标签页和工作台。仅重新加载扩展，不能保证旧标签页里已注入的内容脚本同步更新。

### 尚未解决的边界

- 当前界面在浏览器接受下载任务后返回成功，尚未持续监听最终中断状态。
- iframe 兜底只能尝试启动取包，不能证明文件已经保存。
- 本次浏览器回归使用 22 字节空 ZIP，验证通信和落盘链路；没有验证真实业务权限、压缩内容或大文件传输。
- 用户更早一次“XHR 下载完但没有保存”的原因，不能由本次 HAR 单独还原；不将其直接认定为同一根因。

## 2026-10-27：并发翻页不能只验证空结果与任务池

- 以用户最新HAR的真实条件做基准：1597条结果、我方文号条件8162字符、文件描述ID条件23642字符。每页20条约15.92秒，每页100条约15.79秒，证明主要是每次重复查询的固定开销，不能未经实测假定“每行一秒”。
- 优先减少请求次数：UI默认100条；全选复用当前100条页，1597条只需总计16次查询，而非80次。在相同筛选条件下，6个100条请求真实同时启动，约33.8秒取回600条；不能仅靠空结果或mock耗时承诺业务提速。
- 完整验收包括工作台按钮、后台转发、内容脚本、真实Network起止时间，以及最终不同文件数，不能只断言`Promise.all`或测试数量。
- Vue `defineModel` 的受控值需要等父组件渲染回流。同一轮并发响应若各自读取旧模型再整体赋值，会互相覆盖；本次回归在旧代码上出现1597条只留下397条。批次必须用独立累积对象合并，再同步模型。
- 批次固定条件、查询来源、分页布局与generation。新查询、手动取消或卸载停止旧批；晚到结果不能回填。创建新分页来源的第一页要保留普通查询的取消语义，只有后续绑定同一来源的页面走batch并发。
- 登录中断后，未派发页也属于未完成页。失败列表应从全量页扣除已成功页，而不是只记录发出过但失败的页。
- 构建文件变新，不等于现有浏览器页面已加载新代码。本次用v1.4.2及默认100条作为可见核对项；重载扩展后还要刷新EASY标签页与工作台。

回归入口：[组件批量分页](../tests/unit/ui/file-search-bulk.test.ts)、[分页池取消与完整性](../tests/unit/ui/page-pool.test.ts)、[完整插件浏览器验收](../tests/e2e/file-pages.e2e.mjs)。

## 2026-10-27：折叠布局不能作为字段不可用的依据

- 原站 `FileSearch.js` 通过 `#is_file` / `#is_case` 内的 `a.img_hide` 表示整段折叠，通过 `js-toggle-hide` 标记“更多”暂时隐藏的行。这些行的条件仍然有效。扫描器若把它们的 `display:none` 记作字段不可用，工作台在查询后同步最新字段就会删掉“文件描述、文件来源、附件名称、设置下载文件名称”。
- 判断要区分布局折叠和配置隐藏：跳过确认属于折叠操作的行隐藏；保留控件、单元格和配置类的真实隐藏。不要无条件把所有隐藏字段展示出来，也不要为读取布局展开原站或改写条件值。
- 回归同时覆盖整段折叠、“更多”折叠、配置隐藏、控件隐藏，以及工作台真实同步字段的路径。

## 2026-10-27：下载慢要拆开命名、压缩和浏览器交接

- 最新 HAR 的 `GetFileName` 是每批20个逐批等待，单批约23–28秒，截取到16批；抓包中没有 `DownLoad`。这份证据直接证明命名阶段串行，不能笼统称作“压缩慢”，也不能由页面 HAR 缺少下载请求直接断言下载链路断了。
- 对命名使用6个工作者、每批20个。原站返回的名称只有分号分隔列表，没有文件ID；结果必须按请求批次的原始偏移写回，不能按返回先后追加，否则并发会把名称套到错误文件。
- 任一批失败、返回缺名或登录失效，停止派发并取消其余请求；不把部分成功结果交给压缩接口。进度只累计验证成功的文件数。
- 不盲目放大批量：真实100个一批超过90秒仍未完成；6批各20个的120个文件实测全部成功，最慢56.287秒。命名超时从60秒调整到120秒留出波动余量；实际服务器负载决定收益，不承诺6倍提速。
- 下载按“生成下载名称 → 打包压缩包 → 交给浏览器”分阶段显示。每次操作使用独立关联ID，卸载移除监听，忽略其他任务的事件。下载与全选/补页互斥，避免共用彩虹条互相覆盖。
- 翻页完成保留结果，直到新任务、用户操作清理或离开页面；不能结束2秒后直接清空。浏览器接受下载任务只表示交接成功，提示使用“已交给浏览器下载”。

本次验证与边界见 [文件条件和下载优化验收](file-ui-download-fixes-2026-10-27.md)，入口为 [命名乱序与失败测试](../tests/unit/mail/download-name.test.ts)、[HTTP 下载 E2E](../tests/e2e/download.e2e.mjs) 和 [进度组件测试](../tests/unit/ui/file-search-bulk.test.ts)。

## 2026-10-27：模板的动态控件与实际下载必须共用完整配方

- 原站 `FileSearch.js/selectTemp` 将 `new_filename` 与 `file_name_type` 按分号逐项拆开，`colname` 回显字段，`txt` 回显“固定字符”及文本。界面只写死 `selfilename1` 即使后台读取完整模板，也不能展示或修改后续段。
- 选中模板时展开完整配方；用户修改后传递整份当前配方，并去掉 `templateId`。否则命名阶段的模板重新读取会覆盖界面编辑，形成“看起来改了，下载没有改”。
- 区分元数据异步刷新与用户显式选择：同模板的字典刷新不能覆盖正在编辑的内容；用户重选同一模板、选择空项或恢复模板，则应清理旧编辑。
- “未设置名称”和“名称无效”不是同一状态。无效配方除了阻止当前下载，还需沿组件事件传递原因，阻止绑定客户；若统一变成 `null`，绑定会删掉客户旧命名配置，后续发文退回原名。
- 回归应从真实查询组件选择模板，并断言修改后 `GetFileName` 参数，而非仅测试分号拆分函数。浏览器还要检验全部段、固定字符、换行展示，以及模板切换。

完整记录：[动态下载名称修复](file-download-name-editor-2026-10-27.md)。

## 2026-10-27：长时间打包不能依赖总时长超时和长消息响应

- 原站`DownLoad`是准备压缩包的JSON请求，完成后给`file_guid`，随后才用`FileHandler.ashx`传输ZIP。文件传输进度归浏览器；准备阶段的响应字节不是ZIP下载字节。没有取包编号前不能凭空构造可用的下载地址。
- 旧插件把准备请求固定在300秒中断，1605个文件触发此限制。v1.4.5针对该接口取消总时长定时器，保留网络/HTTP错误、显式取消及其它接口的超时策略，不自动重发打包。
- 仅延长fetch超时仍让长操作绑定后台消息生命周期和工作台30分钟预算。改为后台按原会话检查后转发，EASY内容脚本立即返回任务受理；内容脚本独立准备、发起浏览器下载，再通过关联ID推送最终结果。
- 分块读取的只是打包JSON，可报告实际收到的响应字节；15秒状态消息表示任务仍在等待，不伪造压缩百分比。ZIP保持浏览器直连取包，不转成工作台Blob。
- 无总时限不等于永久卡住：状态消息为失联检测续期，只有10分钟没有任何合法状态才结束界面等待；来源标签页关闭立即报错。组件卸载取消界面等待并清理监听，EASY页面上的任务继续。不要在界面失联后自动再次打包。

验证与边界：[长时间打包修复](file-download-long-pack-2026-10-27.md)。
