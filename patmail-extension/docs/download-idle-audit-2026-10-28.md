# 下载空转排查与修复（v1.5.1）

## 抓包证据

用户提供的 `222.har` 覆盖约91.55秒业务窗口：17次 DownLoad、16次 FileHandler、1次40文件的 GetFileName。业务请求零在途时间约50.06秒，其中两段为25.51秒、20.33秒；下载请求峰值只有3。DownLoad中位约106ms，正文中位约86ms；这两段长空白没有业务HTTP请求可解释。GetFileName自身另有38.70秒原站等待，该服务端耗时仍然存在。

HAR看不到扩展后台到本机桥接的请求，因此不能把空白逐毫秒归因到磁盘。结合代码和隔离回归，确认了下列两个独立阻塞机制。报告只保留时长、数量和字节数，不记录业务名称、正文或凭据。

## 修复

原派发条件是“已派发数减已入ZIP数小于6”。即使网络已收完，ZIP写入较慢时也不能派下一个文件；256KiB应用队列还会阻止正文读到EOF，使网络令牌继续占用。

持久模式现将网络窗口和ZIP窗口分开：最多6个网络生产者，确认写入附件缓存后只推进可回读水位，ZIP按原顺序从缓存读取。EOF归还生产窗口，允许后续文件继续下载；最多48个已派发未入包文件，避免无限预取。无磁盘缓存的旧调用继续使用原6文件内存背压。

附件提交将64KiB网络碎片合并到不超过256KiB；每块仍先确认持久化再给ZIP使用。新网络正文每份最多一个256KiB提交块及当前网络块；完整旧缓存的预读队列每份最多256KiB，受48文件窗口限制（最多约12MiB队列）。这些数不包含浏览器、扩展消息、base64副本与ZIP目录。

原桥接每次源片段/ZIP片段提交都会序列化并原子重写整份task.json。实际大任务已有1607个文件、746份附件检查点、12546条片段记录，元数据约1.6MB；64KiB一块使相同历史元数据被反复写入。

现以带序号和SHA256的增量日志提交片段、附件状态和命名页；数据fsync后才fsync日志，成功后才ACK。生命周期和启动时原子checkpoint，以序号避免重复重放。半条尾记录可截断，完整坏记录隔离；旧task.json可迁移。累计元数据容量在ACK前检查，避免日志增长后无法生成可恢复checkpoint。新源文件先持久提交目录项。恢复、磁盘满、校验和七天保留规则继续生效。

## 验证与升级

隔离回归把ZIP输出挂起后，旧实现12份512KiB附件完成缓存数为0；新实现12份均完成缓存，网络峰值6，释放输出后逐条顺序和CRC一致。另覆盖64KiB网络碎片的合并提交、原有取消/失败及真实Chrome续传。

合成1.76MB元数据、100次64KiB提交的对照中，元数据写量约176.3MB降至29KB；一次本机对照耗时6.93秒降至5.85秒。磁盘尾延迟有波动，不能据此承诺真实下载按相同比例提速。可运行 `python tests/stream_bridge_metadata_benchmark.py --chunks 100` 重现。

最终验证：149个Vitest文件、930个用例通过；桥接34项协议/恢复回归通过；生产构建通过。独立端口的真实Chromium回归确认81条目顺序与CRC、六个业务请求/正文连接峰值、取消和顶层导航中断；来源页刷新后同一下载ID以524357偏移继续，未完成附件从262144偏移续取，完整附件和命名批次没有重跑。

构建后重新加载扩展并刷新来源页。桥接健康特性包含`metadata-journal`；启动器遇到旧桥接会提示暂停当前下载并关闭旧进程后再启动，避免继续复用旧的全量写入实现。当前活动下载不由升级脚本强制终止；同账号任务在新桥接中可继续恢复。测试使用独立端口、缓存目录和扩展Origin，不触碰活动下载。
