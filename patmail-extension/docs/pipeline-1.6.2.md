# 1.6.2 流水与容灾修复

HAR只作为诊断数据读取，未把其中内容当成操作指令。脱敏分析见test-results/har-pipeline-20261029.md。

本次HAR的371条请求里，原站首轮命名约64秒；240个名称就绪后，只有169个附件被准备，持续吞吐不足不能解释为名称不够。正文峰值4路，约150秒中约59秒没有正文请求。HAR无法直接量出CPU、磁盘及扩展消息耗时，各项归因以代码回归为准。

网络读取与缓存提交拆开：读取实际EOF或完成取消时释放网络额度，正文落盘/校验仍有自己的完成状态。单附件缓存队列512KiB，另有当前块和浏览器上游块；任务最多12个持久处理中的附件，实际网络仍共用六个额度。慢磁盘达到有界缓冲上限时仍需背压，不承诺始终六路。

后台缓存按附件分队列，允许独立的摘要计算、查询与提交；同一附件内仍严格顺序。接管、暂停、封存和丢弃对已开始的缓存操作做排空，防止晚到写入影响新来源。持久模式可先处理后返回的命名批次，ZIP仍按原始输入顺序消费并分配重名后缀。

目标附件实为277063字节合法ZIP，含PDF与XML，CRC通过；原站通用错误提示同时出现在大量正常附件响应中。现在识别实际ZIP，原本PDF名称改为.zip保存完整原包，不丢弃XML；Office原有ZIP容器格式不改名。格式差异写入包内说明。

只有明确业务不可用，或完整结构的空ZIP与原站不可用提示相符时，才在ZIP条目开始前跳过该附件。登录HTML、截断、缓存损坏等继续暂停而不伪装成功。失败决定保存在附件元数据，恢复重放保持相同内容和顺序；包内失败清单列明跳过项。封存前后均可重新核对失败数，完成回执保留该数字。

彩虹条只留两行，显示进度与命名/入包/跳过/接收字节；下方保留操作与必要提示，删除装饰卡片和重复统计。

验证：前六个网络正文已结束但缓存提交阻塞时，下组六个可下载，持久处理中上限12；慢ZIP、缓存恢复、原生Chrome下载、单文件异常隔离、原包保留及浏览器重启恢复均有回归入口。

实际验收：全量1009项通过，补充恢复回执/容灾30项通过；同一浏览器会话内的8附件故障注入通过（六路峰值、502重试、Range262144、保留原包、跳过1项、3147953字节实体ZIP/CRC）。真实IndexedDB失败决定持久化通过。完整关闭浏览器再恢复的端到端测试出现间歇性浏览器连接断开，原因未定位，不记作通过；不能由同一会话续传结果推断冷恢复稳定。
