# v1.4.2 文件管理全选性能修复

## 最新 HAR 暴露的问题

用户于 2026-10-27 提供更新后的 `222.har`：39条请求，其中8条 `GetSearchFiles`、29条登录检测。查询条件包含8162字符的我方文号列表和23642字符的文件描述ID，结果总数1597。

第2–7页每页20条，分别耗时16420、15686、16050、15902、15559、16006毫秒。浏览器blocked排队只有约2–8毫秒，时间主要在等待服务器响应；后一页在前一页响应后才发出，查询峰值为1。不能将这份记录解释为“已并发，只是浏览器连接数显示成一条”。

磁盘构建文件已经更新也不代表已打开的页面、后台和内容脚本都加载了新代码。因此本轮除构建外，还将版本标为1.4.2，并核对独立测试浏览器实际运行的manifest版本、完整UI流程和CDP请求。

## 同一真实条件的服务器基准

所有请求沿用最新HAR的完整筛选，没有移除文号或文件描述条件，也没有用空结果代替重查询。

| 请求 | 返回 | 耗时 |
| --- | --- | --- |
| 第1页，每页20条 | 总1597，返回20 | 15919 ms |
| 第1页，每页100条 | 总1597，返回100 | 15792 ms |
| 第2–7页，每页100条，六路并发 | 返回600，全部成功 | 总33788 ms |

六路请求在14毫秒内全部启动，各页约19.4–33.8秒完成。服务器负载会影响每页耗时，不能把6路并发直接承诺成6倍速度。

结论是优先减少重复查询：20条要80页，100条只需16页。此前“100行大概率要100秒”的判断没有实测依据，本次基准显示100条与20条耗时相近。

脱敏原始记录：`test-results/file-heavy-benchmark.json`。

完整脱敏记录：`test-results/file-pagination-live-optimized.json`；过程日志：`test-results/file-pagination-live-optimized.log`。临时浏览器已关闭，用户原有浏览器配置和模板未被此验收脚本修改。

## 实际修改

- 文件查询默认100条。全选复用已经读到的100条页，只补其余页；1597条总计16次查询，全选阶段只补15次。
- 若当前已按20或50条查询，全选先建立100条布局的查询来源，再切换显示和续页，不把原分页来源混入新布局。
- 后续页面保持六路并发，冻结筛选、来源ID和查询代次；新查询、离开页面或手动改选会停止旧批次。
- 建立新布局来源的第一页保留普通查询的取消语义；后续已绑定来源的页面才走免取消的batch通道。
- 修复受控Vue模型的并发覆盖：同一轮多页返回时，原代码会各自基于旧prop赋值，回归测试中1597条只留下397条。现在批次内独立累积，再同步界面。
- 修复登录中断后未派发页未计入待重试列表。已成功页保留，其余页全部返回待补列表；登录中断不立即自动空转重试。
- 修复全选完成提示误数ref对象；修复取消选择后晚到页恢复勾选。

## 让当前 Chrome 使用新版

当前用户Chrome的电脑操作因工具无法可靠识别浏览器URL而被停止，本轮没有继续接管该窗口，也没有声称替用户完成了重载。

使用 `patmail-extension/dist` 的 PatMail 在扩展管理页重新加载后，再刷新EASY原站标签页和工作台。以工作台页脚 **v1.4.2** 和默认 **每页100条** 为核对点；只看到磁盘修改时间不足以确认浏览器运行版本。
