# 下载刚开始即暂停：启动回执预算修复

## 现场证据

通过原 Chrome 的 CDP 读取 EASY 控制台历史错误。最近一次后台超时的第二层栈位于 content.js 第 1 行第 120797 列；核对实际加载的脚本，该位置为 `await command({ action: 'start', ... })`，不是 ZIP write。2026-10-31 10:04:06.214（北京时间）前台已报超时，Chrome 下载项 #282 却在 10:04:08.992 才创建、收到 0 字节后中断。这证明启动仍在后台继续，前台先放弃等待。

后续同一工作台的 495 个附件任务于 10:17:23 完成，下载项 #283 确认为 complete，文件 659404073 字节。ZIP 有 493 个附件和 1 份下载清单，全部 CRC 校验通过。两个不可用源附件分别返回 Word HTML 和 EML，均重试三次后跳过；有正常来源 ZIP 按 ZIP 保存。

现场报告及 ZIP 检查结果位于被 Git 忽略的 `test-results/start-receipt-live/`，不含登录凭据。

## 根因和改动

- 流命令的 start 原来沿用普通 status 的 20 秒等待。后台启动前会恢复连接和重新检查登录；一次复查最多三次、每次 12 秒，加两次 250ms 间隔。冷后台可能串行执行两次复查，之后原生下载导航还有 15 秒连接预算。20 秒小于正常启动路径。
- start 改为等待同一次请求的 130 秒回执，不重发有副作用的启动命令。此预算覆盖已知的会话和导航等待；存储和旧目标关闭仍取决于实际完成时间。
- 浏览器 start 携带 expiresAt；后台在排队前、恢复/打开目标后、最终返回前检查期限。超过期限不会继续交付无人接收的 lease，已打开的目标会关闭，任务和缓存保留。
- 前台在启动等待中暂停时，迟到回执只暂停它返回的 token，避免按 taskId 误暂停后来的恢复请求。
- 后续流 RPC 错误保留初始化、名称检查点、写入、缓存、保存确认或状态查询的阶段。UI 只把旧的纯受理超时映射为“回执尚未确认”，不再吞掉流任务的具体错误。

## 回归

单元回归先在旧实现复现失败，再验证超过 20 秒的启动等待、等待中暂停的迟到回执清理、启动期限前后竞态、阶段错误显示，以及原有流式下载、消息通道和会话检查。

真实 Chromium 回归通过 `PATMAIL_PIPELINE_START_DELAY=1` 注入前 24 秒内的慢登录复查响应，验证只发出一次 start、跨过旧的 20 秒预算后进入下载；随后继续验证正文中断、续传、不可用正文跳过、ZIP CRC 和浏览器完成回执。

本轮结果：9 个相关测试文件、131 项测试通过；真实浏览器测得启动至可见接收约 27.5 秒，只启动一次，并完成 256KiB Range 续传、6 个正常附件和 2 个不可用附件的最终归档。`pnpm build`、`pnpm verify:dist` 和 ESLint 基线门禁通过（仓库仍有既存 lint 问题，不表示全库 lint 零错误）。
