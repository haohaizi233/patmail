# 长时间压缩准备与浏览器下载交接（v1.4.5）

## 证据与根因

用户提供的请求包含1605个`file_no`和对应1605个`file_name`。旧`EasyTransport.waitMs('fileDownload')`返回300000，在`sendForm`中创建总时长计时器，到时主动abort，与用户描述的5分钟取消一致。

原站`public.js`的`DownLoad`通过Ajax请求`BaseInfo.ashx`，收到JSON后将`file_guid`、可选`file_size`交给`GetFile`。`GetFile`把隐藏iframe指向`FileHandler.ashx?guid=...`，由浏览器取包。该Ajax调用本身没有设置5分钟超时。

因此准备包和下载ZIP是两个阶段。插件已有浏览器直连取包，但准备阶段被固定总时长掐断。取包编号没有返回前，不能提前构造真实下载URL，也不能把打包响应大小当成ZIP大小。

## 改动

- 只对`fileDownload`取消总时长定时器；仍处理HTTP、网络、登录错误和显式取消，不自动重发打包。其它接口保留各自时限，测试注入的短时限仍有效。
- 长下载采用短受理、独立执行和独立结果。工作台先注册关联ID监听，经现有后台会话校验转发；EASY内容脚本立即确认受理，异步执行命名、准备和浏览器交接。最终结果独立推送，不把整个操作挂在后台长消息事件或30分钟工作台等待上。
- 准备时每15秒报告等待时间；响应有分块时按真实字节累加显示“打包响应KB”。不伪造压缩百分比，不读取ZIP二进制。
- JSON返回有效取包编号后，立即沿原`chrome.downloads`链路交给浏览器。浏览器右上角继续显示文件传输进度。
- 来源页关闭立即结束界面等待；10分钟没有任何合法任务状态才判定失联，状态不断则持续续期，绝不是10分钟打包总时限。工作台卸载清理监听与等待，EASY来源页仍可继续准备并交接下载。

## 验证与边界

回归入口：

- `tests/integration/easy/download-timeouts.test.ts`：6分钟不回首包仍成功、不取消不重发；7分钟分块响应持续增长并完整解析中文JSON；显式取消仍生效；运行时持续报告存活且最终返回FileHandler地址，结束后清理定时器。
- `tests/unit/ui/download-job-bridge.test.ts`：短受理、独立结果、错误来源与ID忽略；32分钟持续状态不提前结束；来源标签页关闭、状态失联、取消均清理监听。
- `tests/e2e/download.e2e.mjs`：构建后的真实扩展短受理后接收分块打包响应，验证响应字节增长，最终浏览器下载记录及ZIP字节；仍检查六路命名与文件名对应。
- `tests/e2e/download-editor.e2e.mjs`：工作台真实按钮通过后台受理与最终结果完成流程，修改配方仍进入命名请求，失败正确显示。

上述长时用例使用假时钟验证客户端逻辑，不是1605个业务文件在真实服务器上的压缩耗时测试。本次没有为验收重复创建1605个文件的真实压缩包。移除客户端截断不会加快服务器压缩，也不能阻止网关或服务器自身返回超时错误。

EASY来源标签页须保持打开，刷新或导航导致任务状态停止后会判定失联；工作台可以离开，准备完成后仍由EASY页面交给浏览器。浏览器接受任务后的实际传输与中断请看浏览器下载记录。

日志与产物（不入库）位于`test-results/download-long-*`、`download-job-*`、`download-e2e.json`。

## 本次验收结果

- 完整测试133个文件、851个用例通过；类型检查、工作台和内容脚本构建通过，产物版本1.4.5。
- 浏览器回归：先收到`DOWNLOAD_FILES_ACCEPTED`，分块打包响应的字节数逐步增长，随后收到独立最终结果。141文件六路命名、一次压缩、一次浏览器取包，下载记录`complete`且22字节夹具ZIP落盘一致。
- 工作台真实按钮动态配方下载回归通过；1597文件全选依旧只补15页、并发峰值6、完成彩虹条保留。
- 独立代码复核提出的来源页关闭后永久等待问题已补先失败后通过的生命周期测试并修复，复核未发现剩余重要问题。
