# 保存的查询模板没有恢复下载命名配置

## 故障与根因

选用已保存的查询模板时，查询条件能够恢复，但其中的 `filetemp`、`selfilenameN`、`txtfilenameN` 不会用于下载命名。下载得到空的命名选择后使用附件原名，同案件的不同原名也不会被合并为相同的最终模板名。

`parseQueryXml` 将这些非业务筛选字段保存在 `unknownFields`；`resolveQueryTemplate` 正确地把它们排除在 `GetSearchFiles` 之外。然而 `QueryTemplateSection.formValue` 只读临时值和已经过滤的查询字段，没有读取模板保留的下载控件。手动选取下载名称模板的旧测试不会经过这个故障入口。

保存模板也存在同类遗漏：`saveBoth` 保存业务筛选和旧的 `unknownFields`，没有写入当前编辑后的命名配方，后续重新选用时会丢失修改。

## 修复

- 下载控件从模板保留字段恢复，临时覆盖仍优先；业务查询参数保持独立。
- 无模板 ID 的自定义配方恢复完整的最多 31 段，包括固定字符。无效配方显示错误并阻止下载和保存。
- 保存时替换旧下载控件，写入当前的模板 ID 或完整自定义配方；清空后保存会删除旧设置。
- 保留原有规则：同案件按最终下载名去重、doc/docx 视为同类、保留上传最新者；不同案件独立，附件原名中的数字括号仍是字面字符。

## 验证

新增 UI 用例先在旧实现复现：加载带 `filetemp` 或多段名称的历史 XML，`currentDownloadSelection()` 返回 `null`。修复后通过。

针对命名编辑、保存与重新加载、查询参数隔离、去重、名称预览、文件全选、流式下载和下载 API 的 8 个单元/集成测试文件共 111 项通过。

`node tests/e2e/diy-dedupe.e2e.mjs` 使用隔离扩展和模拟 EASY 响应，从选择保存的查询模板开始，检查实际命名请求、去点后的 `DownLoad.file_name`、同案件最新赢家和跨案件保留，以及最终 ZIP 名称和正文 CRC。结果见 `test-results/diy-dedupe.json`。

`node tests/e2e/download-editor.e2e.mjs` 通过：一次查询后修改配方、两次实际 ZIP 下载及 CRC、无效配方拦截、暂停和丢弃、浏览器冷重启恢复。该测试原先要求进度文案包含“下载文件”，但现有界面已经用“导出完成”作摘要；本次更新为检查取名/入包计数，同时保留 100% 和完成状态断言。

生产构建和构建产物校验通过。ESLint 基线门禁通过；仓库仍有既有 lint 问题，直接 ESLint 不等于零问题。

现场 ZIP 仅检查了条目元数据：788 个条目，保留了原始名称，未匹配到带校验点的申请号。该 ZIP 本身不能单独证明去点算法失败。浏览器回归另用带点的申请号验证最终去点结果。未重新下载整批真实业务附件。

更新扩展后需重新加载 EASY 来源页和工作台。已开始/暂停的下载沿用冻结配置，需要丢弃旧任务再启动新任务才能使用新配方。
