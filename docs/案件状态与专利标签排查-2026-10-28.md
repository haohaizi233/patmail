## 一、案件状态：期限监控正确、文件管理不对的根因

### 原站数据与口径

`IPGetBasicData`（FileSearch.aspx 用）的 `CaseStatus` 与 `LimitMonitorInit`（LimitMonitor.aspx 用）的 `case_status` 是同一批 158 行，字段名不同：

| 来源 | 字段 | 说明 |
| --- | --- | --- |
| `CaseStatus`（文件管理） | `case_status` / `case_status_id` / `case_type_id` / `status_class` | 158 行 |
| `case_status`（期限监控） | `value` / `text_zh_cn` / `case_type_id` / `status_class` / `seq` | 同 158 行 |

- `status_class` 分布：CASE 110、ALL 14、PROC 34。PROC 是年费类状态（“第1年年费…第6年年费”），不进案件状态树。
- 跨案件类型同名重复：未递交 ×4、结案 ×6、已完成 ×3……同一案件类型内没有重名（专利子集 57 条无重复）。
- ALL 类 14 条全部挂在专利（一通~九通、一补~三补、复审、无效）。

原站两页的下拉树都是同一句过滤（`docs/js/FileSearch.js:382`、`:895`；`docs/js/LimitMonitor.js:742`）：

```js
if ((row.status_class == "ALL" || row.status_class == "CASE") && row.case_type_id == $("#case_type").val()) { … }
```

即：**只放 status_class 为 ALL/CASE、且属于当前案件类型的行**。文件管理页的案件类型下拉默认选中专利（DOM 里 `<option … type_code="P" selected="selected">专利</option>`，`FileSearch.js:855` 追加选项后再 `trigger('change')` 重建树），期限监控页的 `#case_type_id` 第一项就是专利。所以原站默认展示的就是专利的 57 条（快照 `file-search-form.snapshot.json` 里 case_status 正好 57 个选项，与现拉数据一致）。

### 插件差异

- 期限监控表单（`LimitQuerySection.vue`）：`caseTypeFor` 在案件类型为空时回落 `CURRENT_ENVIRONMENT.caseTypeId`（专利），再走 `choicesFromDictionary`（内部已按 `case_type_id` + ALL/CASE 过滤、按 seq 排序、同名去重）→ **57 条，正确**。
- 文件管理表单（`QueryTemplateSection.vue`）：`liveChoices` 只有在选了案件类型时才过滤，**案件类型为空就把 158 行全量倒出**——出现 4 个“未递交”、6 个“结案”，还混进 34 条年费类 PROC 状态。同一问题也影响申请类型、业务类型、客户状态、处理事项（同样按 `case_type_id` 收窄的字典）。
- 缓存回退（`option-fallback.ts` 的 `savedChoices`）把未收窄的全量存了下来，接口没回来时兜底同样混型。
- 查询参数其实和原站一致：`file-search-params.ts` 里案件类型留空时会按 `CURRENT_ENVIRONMENT.caseTypeId`（专利）提交，下拉却展示全量，选中商标的“未递交”后按专利查永远查不到。

### 修复

1. `QueryTemplateSection.vue`：`liveChoices` / `storedLabel` / `optionsFor` 统一按 `案件类型 || 当前环境默认专利` 收窄（新增 `effectiveCaseType()`），与原站下拉、查询提交、期限监控表单同口径。
2. `option-fallback.ts`：`SavedChoice` 带上 `caseTypeId` / `statusClass` 归属，`choicesFromDictionary` 从字典 metadata 写入，新增 `scopeSavedChoices()` 在读取缓存时按同一口径收窄；旧缓存没带归属时原样返回，不做猜测。
3. `LimitQuerySection.vue`：`caseTypeFor()` 对所有按案件类型收窄的字段都默认专利（原来只给案件状态兜底，申请类型/业务类型等在案件类型为空时也会混型）。
4. 递交管理表单（`FilingSearchQuery.vue`）此前已按 `案件类型 || 默认专利` 收窄（申请类型等），未改动取数逻辑，三张大表现在同口径。

## 二、专利标签：“下拉框变文本框”的根因

### 原站控件（DOM + JS + 三方作用）

- DOM：`#apply_tags_id`（文件管理）、`#apply_tags_id_other/_fee/_Errorfee/_returnfee`（期限监控）都是
  `<input type="text" … tree_id="tree_apply_tags_id" objid="" …>` —— TreeUser 组合控件的“文本框”半边，面板（下拉树）由 zTree（`jquery.ztree.all-3.5.min.js` + `exhide`）+ `public.js` 的 TreeUser 插件生成，样式 `li_down`，操作条含 搜索/查询/清除/确定/全选（多选 checkbox）。
- 选项来源：`GetApplyTags` 的 `ApplyTags`（每项 `id`/`name`），提交取 `$("#apply_tags_id").attr("objid")` 逗号拼的内部 ID（`FileSearch.js:1052`、`:2086`；`LimitMonitor.js:1323` 等）。
- **三方 JS 的关键作用**：`FileSearch.js:871-876`、`LimitMonitor.js:30-39` 都是 `if (_Meta.ApplyTags) { … $('#apply_tags_id').TreeUser(…) }` —— **只有标签数据非空才初始化 TreeUser**。

### 本次实测（带 CK）

`CaseInfo.ashx GetApplyTags` 与 `PatentAction.ashx GetApplyTags` 都返回 204 字节：`{"ClientInfo":{…},"ApplyTags":null}`。当前租户没有配置专利标签。

于是原站上这个控件**没有被 TreeUser 初始化，就是一个普通可编辑文本框**：可以打字，但提交只取 `attr("objid")`（恒为空），打的字永远进不了查询。这就是“专利标签下拉框变文本框”的根因——不是样式问题，是数据为空时原站 JS 跳过了下拉初始化。

### 插件口径与本次修复

插件对这类字段的口径：**只收内部 ID，必须按树形下拉呈现，不能退化成自由文本**（手打名字查不到）。此前已修扫描器把带 `tree_id` 的控件判为 picker（`0f306a2`，专利标签等 6 个字段不再退化）。本次把三个大表里剩余的“下拉退化成文本框”兜底收口：

1. `QueryTemplateSection.vue`、`LimitQuerySection.vue`：named 字段（原站 TreeUser/下拉字典字段）不再落到自由文本输入框，选项没读到也保持下拉呈现（不会再出现手打名字查不到的文本框）。
2. `FilingSearchQuery.vue`：同上，只保留“签约单位（business_coop）”一个显式允许手填的例外（原样保留提示文案）。
3. `TreeOptionSelect.vue`：树为空时给出“没有可选的选项。原站没有返回这个下拉的数据。”——专利标签这类空字典不再表现为一个打不开的空下拉。

## 三、核对结论速查

| 项 | 原站 | 插件（修复前） | 插件（修复后） |
